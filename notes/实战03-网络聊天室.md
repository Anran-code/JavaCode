# 实战03：网络聊天室

对应客户端 `anran-network-chat-sys` 和服务端 `anran-network-server-sys`。使用 Swing、TCP、线程、集合和文件流实现昵称登录、在线名单、群聊、私聊、未读提示与最近 50 条私聊历史。

## 1.整体结构：

```text
客户端 A ── Socket ── 服务端 ── Socket ── 客户端 B
                     │
                     ├── 在线连接与昵称映射
                     ├── 群聊广播、私聊转发
                     └── 本次运行的私聊历史文件
```

客户端之间不直接连接。服务端接收客户端消息，再决定发给所有人还是某个对象。

| 类 | 职责 |
| --- | --- |
| ChatEntryFrame | 获取昵称、建立连接、发送登录消息 |
| ClientChatFrame | 群聊界面、在线列表、统一发送与私聊窗口管理 |
| ClientReaderThread | 读取服务端消息，按消息类型分发 |
| PrivateChatFrame | 展示某个会话、合并历史和实时消息 |
| ChatMessagePane | 统一处理文字样式和左右对齐 |
| Server | 监听连接、启动客户端处理线程、管理在线连接 |
| ServerReaderThread | 解析一个客户端的消息，执行广播、转发与历史查询 |
| PrivateHistoryStore | 私聊文件的保存、读取和清理 |
| PrivateMessage | 私聊结构化数据及统一读写顺序 |
| Constant | 两端一致的消息编号和连接配置 |

## 2.启动、登录与线程分工：

先运行服务端 `Server.main()`，再运行客户端 `App`；可以启动多个客户端。当前客户端连接 `127.0.0.1:6666`。跨电脑时要改成服务端可达的局域网 IP，并保证端口可访问。

登录流程：校验昵称 → 后台线程创建 Socket → 写入登录类型与昵称 → 在 Swing 事件线程创建聊天界面 → 启动统一接收线程。

| 线程 | 工作 |
| --- | --- |
| 服务端主线程 | 循环 `accept()` 接收新连接 |
| 每个 ServerReaderThread | 阻塞等待自己负责的客户端消息 |
| 客户端接收线程 | 循环读取同一 Socket 的服务端消息 |
| 客户端后台发送/连接线程 | 处理可能等待的网络操作 |
| Swing 事件派发线程 | 响应界面事件、更新组件 |

按钮事件中直接做网络连接或阻塞读取，可能让窗口卡住。后台收到数据后，通过 `SwingUtilities.invokeLater(...)` 把界面更新交回事件线程。

当前服务端是**每个连接一个线程**，没有使用线程池；不要与 `17-net` 中的线程池练习混淆。

## 3.协议：类型之后是什么？

TCP 提供有序字节流，不会替应用自动划分业务消息。两端通过 `DataInputStream / DataOutputStream` 约定读取顺序。

每条消息先写 int 类型编号，接着按下表写字段：

| 编号 | 方向与用途 | 类型之后的数据 |
| --- | --- | --- |
| 1 | 客户端 → 服务端：登录 | UTF 昵称 |
| 1 | 服务端 → 客户端：在线名单 | int 人数，然后逐个 UTF 昵称 |
| 2 | 客户端 → 服务端：群聊 | UTF 正文 |
| 2 | 服务端 → 客户端：群聊 | UTF 昵称、时间与正文组成的文本 |
| 3 | 客户端 → 服务端：私聊 | UTF 正文、UTF 接收人 |
| 3 | 服务端 → 客户端：私聊 | 一条 PrivateMessage |
| 4 | 服务端 → 客户端：私聊失败 | UTF 对方昵称、UTF 原因 |
| 5 | 客户端 → 服务端：查历史 | UTF 对方昵称、UTF 请求编号 |
| 6 | 服务端 → 客户端：历史结果 | UTF 对方昵称、UTF 请求编号、int 条数、逐条 PrivateMessage |
| 7 | 服务端 → 客户端：历史失败 | UTF 对方昵称、UTF 请求编号、UTF 原因 |

同一编号在两个方向上可以有不同格式，但客户端和服务端必须分别知道自己的读取约定。`readInt()` 读完类型后，接下来只读这类消息的剩余字段。

`writeUTF()` 带有编码长度信息，正文换行不会打乱边界，但编码后的单个字符串有长度限制，并非可以无限长。

## 4.在线名单与群聊：

服务端保存 `Map<Socket, String>`，从连接映射到昵称。当前实际使用 ConcurrentHashMap，支持多客户端线程并发登录、退出和遍历；设计稿中早期的 HashMap 已不再是当前实现。

收到登录消息后记录映射，再广播在线名单。发送名单前先复制出昵称列表，以该快照的 size 和元素编码，保证“人数”与紧随其后的昵称数量一致。

群聊流程：读取正文 → 通过当前 Socket 查发送人 → 服务端添加一次时间 → 广播给所有在线连接，**包括发送者自己**。

客户端用服务端回传的内容显示自己的消息，避免本地先添加一次、收到回传后又重复一次。

## 5.为什么私聊窗口不单独读 Socket？

所有群聊、私聊和名单消息共用登录时建立的连接。客户端只有一个 ClientReaderThread 读取它，再根据类型分发给相应窗口。

如果每个私聊窗口都开线程读取同一个输入流，就可能一个线程读走类型，另一个读走正文，协议立即错位。因此私聊窗口只负责显示与发起操作，不创建新 Socket 或独立接收线程。

## 6.私聊发送与错误处理：

右键在线用户 → 点击“私聊” → 以对方昵称查找或创建 PrivateChatFrame。`privateFrames` 保存“对方昵称 → 窗口”，重复打开时复用已有窗口。

服务端遍历 onlineSocket 的 entrySet，按昵称查目标连接。Map 没有直接“通过 value 唯一查 key”的保证：同一昵称可能对应多个连接。当前代码遇到多个同名接收者时返回错误，不随意选一个。

私聊先保存历史成功，再把同一条 PrivateMessage 发给接收者和发送者。对方离线、昵称歧义或保存失败，返回专门的错误消息；这类业务失败不应直接当作整个连接断开。

写入成功只表示消息已写到本地网络输出流，不等于对方已经阅读。若历史已保存但接收方连接中断，服务端也会返回相应提示。

## 7.锁住一条完整消息：

多个客户端处理线程可能同时给同一目标发送群聊、私聊和名单，必须避免字段交错：

```java
synchronized (target) {
    target.getOutputStream().write(packet);
    target.getOutputStream().flush();
}
```

先用 ByteArrayOutputStream 在内存中编码完整消息，再在同一个 Socket 锁下整条写出。这样既避免并发写入交错，也避免编码中途失败后向连接留下半条消息。

**ConcurrentHashMap 保护集合操作，Socket 锁保护消息写入，两者解决的不是同一个问题。** 客户端不同窗口共用连接发送时也采取同样的整条写入保护。

## 8.未读提示与消息样式：

- 私聊窗口已打开：把收到的消息交给对应窗口。
- 窗口未打开：`unreadMessages` 按对方昵称累计条数，在列表后显示数字。
- 新建窗口：向服务端查询历史，成功加载后才清除未读数；失败时保留提示。

当前未打开窗口时主要保存未读计数，消息正文由服务端历史负责提供。超过 50 条时只保留最近 50 条，因此未读数字可能大于最终可加载的消息数。

ChatMessagePane 使用 JTextPane 的样式：发送人和时间用较小的宋体、深灰色；自己发送的消息右对齐、绿色，别人的消息左对齐、蓝色。消息头和正文分开插入，避免时间重复拼接到正文末尾。

## 9.私聊历史的数据格式：

PrivateMessage 保存：会话内递增 ID、发送时间 sentAt、发送者、接收者、正文。文件与网络共用这套顺序：

```java
out.writeLong(id);
out.writeLong(sentAt);
out.writeUTF(sender);
out.writeUTF(recipient);
out.writeUTF(content);
```

读取时依次 `readLong()`、`readLong()`、三个 `readUTF()`。原始数据与显示文本分离，时间格式只在展示时生成。

历史文件默认放在服务端模块的 `chat-data/private`。双方昵称先排序，再计算 SHA-256 作为文件名，让 A 与 B、B 与 A 共用一份记录，也避免昵称中的特殊字符变成路径。哈希文件名不是内容加密。

每次保存：读取旧记录 → 分配新 ID → 添加消息 → 超过 50 条则移除最早一条 → 写临时文件 → 替换原文件。优先使用原子移动，环境不支持时退回普通替换。

文件还包含格式标识、版本和条数；读取时检查会话与 ID 等信息。损坏文件会报告错误，不直接当作空记录覆盖。共享的 PrivateHistoryStore 用 synchronized 保护读、改、写全过程。

## 10.历史与实时消息如何避免重复？

查询历史的同时可能收到实时消息。PrivateChatFrame 使用：

```java
TreeMap<Long, PrivateMessage> messages = new TreeMap<>();
messages.put(message.getId(), message);
```

以消息 ID 为键，相同 ID 会合并为一条，TreeMap 又能按 ID 升序展示；超出 50 条时通过 `pollFirstEntry()` 删除最早记录。

每次创建窗口生成一个 UUID 请求编号。响应必须同时匹配对方昵称和当前窗口的请求编号，避免旧窗口已经关闭、服务端的迟到结果却覆盖新窗口。

## 11.历史保留范围与退出清理：

当前按你的要求设计为：**仅在本次服务端运行期间保留历史，服务器关闭后清空。**

- 私聊窗口关闭：只销毁窗口，不删除服务端记录；再次打开可加载最近 50 条。
- 服务端正常退出：shutdown hook 清理历史；接收循环异常结束也尝试清理。
- 强制终止或断电：退出钩子可能不执行，下次服务端启动时再次清理残留。
- 服务端先成功绑定端口，再开始清理，避免误开第二个服务端删掉正在使用的记录。

`closeAndClear()` 先禁止继续读写，再清理该存储生成的文件，防止清理结束后仍有线程写回数据。这不是跨服务端重启永久保留历史的方案。

## 12.技术复盘与当前边界：

| 技术 | 项目中的用途 |
| --- | --- |
| Socket / ServerSocket | 建立客户端和服务端连接 |
| 数据流与协议编号 | 识别消息类型，保证字段读写顺序一致 |
| 线程与 invokeLater | 网络等待和 Swing 更新分工 |
| Map / ConcurrentHashMap | 在线连接、私聊窗口、未读数量 |
| synchronized | 防止同一连接写入交错、保护历史文件读写 |
| TreeMap | 私聊历史按 ID 排序和去重 |
| 文件流、临时文件 | 保存有限历史，减少覆盖中途失败造成的数据丢失 |

当前仅用昵称识别用户，没有密码认证；同名登录没有在入口统一禁止，历史会话也以昵称作为身份，不能当作真实账号系统。私聊仅支持向在线对象发送，没有离线消息投递、自动重连或端到端加密；群聊也没有实现文件历史。

排查聊天异常时，优先检查：**两端字段顺序是否一致、同一输入流是否被多个线程读取、同一输出流是否发生交错、业务错误是否被误当成断线。**
